## 交付与复现

入口为 [`scripts/verify_acceptance.py`](../../scripts/verify_acceptance.py)。在服务端工程目录执行，使用当前 `.env` 指定的开发基础设施；`checks` 会应用全部迁移。测试自己创建独立 PostgreSQL schema、Redis 前缀和测试对象，正常退出时清理。

```bash
.venv/bin/python -m scripts.verify_acceptance --stage all
```

默认输出到 `docs/acceptance/runs/<UTC时间>/`，保存命令、退出码、JUnit、源文件摘要、运行记录及判定。当前目录是本次分阶段执行后汇总的记录，不宣称完整入口已从头连续跑过一次。

| 阶段 | 内容 |
| --- | --- |
| `checks` | 迁移、实际存储审查、服务端 `make check`、前端 `pnpm check` |
| `integration` | 全量服务端集成；同时导出 API 和两种结果 schema 的评测报告 |
| `browser` | 启动真实 IAM/渠道临时服务，再执行浏览器套件 |

可用 `--output docs/acceptance/runs/<本轮目录>` 汇总同一候选的分阶段结果。退出码 1 表示命令或用例失败；退出码 2 表示汇总完成但关口仍阻断。缺记录、跳过和失败均不能变成通过。相同参数用例以最新 JUnit 为准，其余参数的失败保持可见。

本机使用 Python 3.12、Node 22 / pnpm 10、Chrome、真实 PostgreSQL、Redis 和 MinIO；硬件、版本和精确源文件摘要见 [环境清单](environment.json)。脚本自动查找工程旁 `.tools` 中的 uv 与 Node 工具；没有本机工具时使用 PATH。基础设施准备沿用工程 README。

## 性能和未完成项

测量固定为 4 个渠道、每渠道 10 个 Agent，渠道配额 5、平台配额 20；每类先预热 20 次，再记录 100 次，六批依次运行。管理查询及业务受理使用本机 TCP；服务受理从已认证上下文直接调用。受理后取消，不执行模型。原始样本、P50/P95、最大值及边界在 [性能记录](performance.json)。

管理查询目标 P95 ≤ 1 秒、无外部等待的受理服务目标 P95 ≤ 500 毫秒；本轮两者均未达标。HTTP 受理另包含真实 MCP 当前主体复核总时延，不把这段总时延冒充扣除外部等待后的平台开销。时延失败保持为失败的 JUnit，未放宽断言。

最终复测使用与三渠道页面验收相同的源码摘要，采样期间未变化。主机为 Apple M1 Pro、10 个逻辑 CPU、16 GiB 内存；Docker 分配 2 个 CPU、4,094,447,616 字节内存。该结果限定于这组本机资源与数据规模。
