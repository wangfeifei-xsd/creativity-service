# 受理并发与配置页面修复

本轮落实 7 项修改。原 3,562.318 ms 为修复前数据；完整回归后的最终同口径复测为 **纯受理 P95 556.992 ms**，P50 459.668 ms，**500 ms 目标仍未通过**，超出 56.992 ms。没有把模型首 Token、模型执行时间计入此指标，也没有用旧管理查询失败记录代替当前结果。

## 修改与行为

| 修改项 | 当前实现 |
| --- | --- |
| 渠道 5、平台 20 的可视化配置 | 渠道工作区增加“并发限额”，平台工作区增加“平台限额”。可新增、编辑和启停，展示当前占用、剩余及状态；平台配置显示生效时间。新增表单分别默认 5 和 20，列表展示实际保存的配置。平台操作校验平台会话和治理权限，渠道操作校验预算管理权限；编辑冲突保留表单。 |
| 已有名额的请求不再等待受理配额锁 | 租约领取、运行进度和已冻结候选读取不再默认取得渠道账本或平台配额锁。实际调用预占、发送登记、结算、释放仍按需取得对应额度锁。回归同时占住渠道账本和平台配额锁，已受理运行仍可领取租约。 |
| 受理 SQL 与 N+1 | 依赖按资源种类批量读取；Skills 的包、文件、工具、权限与模型能力共用本批数据，MCP 按本批连接取最新发现。新增快照、来源和运行记录集中查重与批量写入。参数化查询结构有界复用，所有数据值仍每次绑定、查询。 |
| 同事务重复身份读取 | 同一受理事务中，渠道、环境、域、账号、成员以关联查询加载，授权按完整身份上下文复用。事务外身份校验与事务内提交复核分别保留；撤权、退出、环境变更不能使用旧授权继续提交。 |
| 来源登记与删除检查 | 候选来源改为一次 `link_many`；共享图锁内复用当前事务的恢复屏障和删除标记。简单受理对两表分别只查一次，来源边继续读取事务内最新状态；批量写入后再做运行内容检查。 |
| 重复解析与两次冻结事务 | 正式运行先准备发布映射与依赖闭包，提交事务重读并比对，再完成校验、候选及运行快照、幂等和 outbox。当前请求复用已经解析的执行策略，跨事务和执行边界仍校验。配置竞争返回冲突，预算失败回滚全部新增记录。 |
| 全局锁内加载历史占用 | 平台配置每个代码只返回当前生效版本；并发在数据库中只统计 HELD，请求量只统计适用周期，已释放请求仍计入当期请求数。平台锁移到受理末尾，只保护平台计数、占用登记和提交。新增四个普通查询索引。 |

渠道并发也已从新的 Agent 发布摘要中分离。修改限额、停用策略后无需重新发布 Agent，下一次受理使用当前配置。对旧发布版本，仅用发布时保存的冻结预算版本还原历史渠道并发摘要；历史版本不改写，其他依赖变化仍拒绝。测试覆盖原有发布摘要、提高限额后新增受理、达到新限额返回 429、停用后放行及历史版本保持不变。

## 性能证据与边界

继续使用原验收函数：4 个渠道、每渠道 10 个 Agent、渠道并发 5、平台并发 20；每类 20 次预热和 100 次正式采样，20 个客户端。真实本地 PostgreSQL、Redis；测量期间模型调用为 0。没有修改并发、采样数、目标或 asyncio 事件循环。

最终结果见 [原始结果](acceptance/admission-optimization-20261005/performance.json) 和 [执行日志](acceptance/admission-optimization-20261005/performance.log)。测量期间源码摘要不变，为 `1786012ffd1d3bc60aa220bed169d4e4852fd07c1060f57826f05043e4736cfe`；开始时主机 load average 为 8.368 / 5.413 / 4.789（10 核）。本轮没有其他测试并行执行，不能据此假定宿主机没有其他负载。回归前 588.619 ms 的中间结果保留在 `pre-regression-performance.*`，不作为最终验收值。

| 指标 | 修复前 P95 | 最终 P95 | 目标 |
| --- | ---: | ---: | ---: |
| 管理查询 | 383.813 ms | 282.802 ms | ≤ 1,000 ms，已通过 |
| 已认证上下文的纯服务受理 | 3,562.318 ms | 556.992 ms | ≤ 500 ms，尚未通过 |
| 包含真实 TCP MCP 主体复核的业务 HTTP 受理 | 7,141.514 ms | 2,156.952 ms | 单独记录，不能等同于排除外部等待后的服务开销 |

查询探针与无探针性能测试分开执行，方法耗时包含子调用，不能相加。SQL 次数沿用 SQLAlchemy 执行事件口径，不包含驱动自动 BEGIN、COMMIT、ROLLBACK；批量参数和一条 CTE 内多个普通 INSERT 不按记录条数重复计数。旧证据保留在 `query-fixes-20261004`。

同一最终源码的独立 20 请求探针结果见 [统计](acceptance/admission-optimization-20261005/profile-summary.json) 和 [原始记录](acceptance/admission-optimization-20261005/lock-profile.json)：

| 项目 | 最终诊断结果 |
| --- | ---: |
| 每次受理 SQL 执行次数 | 47～49，平均 47.8；原为 146～148 |
| 恢复屏障 / 删除标记读取 | 各 1 次；原各 14 次 |
| 初始资源取锁平均耗时 | 11.111 ms |
| 渠道账本取锁平均 / P95 | 49.738 / 100.595 ms |
| 平台配额取锁平均 / P95 | 11.197 / 17.727 ms |
| 非锁 SQL await 累计平均耗时 | 330.837 ms |

原先系统锁把完整受理串行化的问题已消除；当前平台取锁平均约 11 ms。剩余开销仍涉及 47～49 次 SQL 往返及渠道账本临界段，下一步应继续定位这两处。SQL await 包含网络、驱动和并发调度，当前证据不能把 330.837 ms 全部认定为数据库执行慢，也不能据此承诺 500 ms 已达标。

## 验证与迁移

`make check` 已通过：格式、lint、318 个源文件类型检查、197 项非集成测试、OpenAPI、模块契约、模型归档和存储审查。完整集成回归 **439 项通过、13 项跳过、0 失败**，耗时 25 分 31 秒，见 [JUnit 结果](acceptance/admission-optimization-20261005/integration.xml) 和 [日志](acceptance/admission-optimization-20261005/integration.log)。跳过项为固定构建组合验收、固定构建浏览器验收、须单独执行的性能测量，以及 10 项须指定固定摘要镜像的隔离运行测试；性能测量已另行执行，其 500 ms 断言未通过。

前端 API 一致性、类型、lint、19 项单测与构建通过；新增限额页面和原预算页面共 6 项浏览器用例通过，页面使用路由夹具。新增渠道及平台限额最后一个名额的并发竞争、额度拒绝的整笔回滚、发布映射/退出竞争均有真实数据库回归。模型响应和外部接收端仍使用受控夹具，不据此声明真实供应商验收完成。

本地开发库已从 `0033_layered_memory` 升级至 `0034_admission_indexes`，实际存储审查通过。迁移仅新增普通索引，不增加表、业务约束或默认值。源码、前端、迁移摘要及验收边界见 [验证清单](acceptance/admission-optimization-20261005/verification.json)，复现命令见 [证据说明](acceptance/admission-optimization-20261005/README.md)。

锁标识不变，统一排序改为“普通资源 → 渠道账本 → 平台配额”。部署时 Web、Worker、补偿与管理进程须统一升级，不能与旧版纯整数排序混用；细节见 [服务不变量](data-model/service-invariants.md)。本轮没有提交 Git 或部署外部环境。
