# 订单 AI 协助配置

这是一组可绑定到现有平台的业务配置。Creativity 核心只增加通用的受限幂等写预授权和结果核查，不识别租号订单、引导类型或工具名称。租号端负责事实、业务资格、一次性执行、合法接收方和消息；模型负责本单情况的分析与解释。

## 装配顺序

1. 核对租号服务是否已有 `rental_ai_guidance` 和 `rental_ai_operation`；缺失时执行 `sql/upgrade_order_ai_guidance.sql`，新库使用完整的 `sql/gamerental_service.sql`。已有环境应核对实际结构，不重跑全库初始化；环境升级记录由租号服务维护。
2. 建立本环境专用 MCP 应用，绑定实际 Creativity 渠道，并通过原 MCP 连接配置鉴权。租号 `gamerental.order-assistant` 默认关闭；准备好 `application-ids`、`principal-ids`、`orders-created-after` 后才启用。`principal-ids` 是创建计划的管理身份转换为 worker 后保持的实际 `principal_id`，不能随意填租客、号主或虚构服务账号。租号不增加平台租户。
3. 在工具管理中发现六个 `rental_assistant.*` 工具，输入输出采用源端发现契约。先配置并发布 `get_operation_status`，再将六份 `*.policy.json` 合并进相应工具配置。它们是策略覆盖项，不是完整的工具创建请求；保留真实 MCP binding、环境和输入输出契约。三个写工具设置 `source_key`、禁止普通重试/缓存，预授权只允许本 Agent 编码、实际执行身份和封闭参数 Schema。`bind_get_operation_status`、`bind_principal` 必须替换为本环境实际资源标识。
4. 将 `prompt.json` 建为提示词配置；将 `SKILL.md` 导入为技能包（或将正文填入技能内容），配置支持文本生成的实际模型路由（可复用“通用模型路由”；原生结构化输出可选，平台始终校验 JSON 与输出 Schema）；发布提示词、路由、技能及工具。模型输出 Schema 与保存工具契约保持一致。运行时每个分析节点仅一次模型尝试，不启用自动输出修复或模型重试。
5. 准备绑定表，包含 `bind_prompt`、`bind_model_route`、`bind_skill` 及六个 `bind_<操作名称>`。使用已有离线工具替换资源引用：

   ```sh
   python -m examples.agents.prepare examples/agents/rental-order-guidance/agent.json .local/guidance-bindings.json .local/guidance-agent.json
   ```

   创建 Agent、执行校验并发布。场景名称和全部步骤均在配置文件中。平台工具参数边界也保存在配置里；修改 Agent 编码时应同步修改三个工具的允许列表。
6. 用 `schedule.json` 创建计划。只有生产用途运行可使用预授权；工具调试仍逐次确认，评测不得真实写入。先用隔离数据验证与业务人员核对模型内容，再启用正式租号授权及计划。

租号源端示例配置（值须来自实际环境）：

```yaml
gamerental:
  order-assistant:
    enabled: false
    application-ids: [实际专用应用标识]
    principal-ids: [实际计划执行身份]
    orders-created-after: 2026-10-08T00:00:00Z
    preparation-minutes: 30
    lease-seconds: 900
```

截止时间是明确的接入范围，启用时设置实际业务切换时间。租号应用的调用方渠道必须等于 Creativity 实际 `channel_id`，不能填写应用名称或渠道显示名称；连接测试和发现成功不能替代业务身份核验。填写错误时可在租号后台修改现有应用，保存会使旧令牌失效，现有密钥继续用于重新鉴权。应用授权还会核对 MCP 令牌验证得出的环境、渠道和应用状态，以及平台身份时效；模型参数不能替换这些字段。

## 工作流与容量

`查找 → 领取 → 分析 → 保存 → 发布 → 结束`。无候选或领取失败直接结束；领取到已保存结果时直接发布，不调用模型。`NO_ADDITIONAL_HELP` 保存评估依据、消耗本类型唯一资格，发布工具返回已跳过，不发消息。

默认每 60 秒处理一个任务，一次分析可生成租客和号主的分别可见视图。此配置用于小范围启用；实际吞吐最多每计划每分钟一个协助任务，不能把它当作高吞吐批处理。源端查询是有界队列前缀（上限 20），不是分页游标。不能只把 `limit` 改大：当前模型输入是 `claim.item`，多任务处理须配置明确的逐任务编排，并复核上下文及预算上限。该扩展应沿用通用工作流能力。

样例上下文上限为 64000 Token、单次运行预算为 96000 Token；需配合支持相应容量的模型路由。实际输入包含提示词、技能、输出契约、步骤结果和工具事实，不能只按订单 JSON 大小估算。开发联调中原 16000 上限在真实订单分析前触发拦截，因此装配前需核对实际输入大小；预算上限不等于实际用量。

发布失败后的下次扫描优先返回 SAVED 任务，原结果在发布时重新核验。领取后没有可靠结果的任务不会被另一运行接管；到期显示 `OUTCOME_UNKNOWN`，通过原 run、模型尝试及 `get_guidance_contexts`/`get_operation_status` 核查。不得删除账本、换类型或换模型重做。后台管理处理入口和自动恢复未知模型结果不在本次实现中。

## 内容与验收边界

展示来源固定为“AI助手生成”。协助与系统消息可同时存在，只有催办或复述状态时应选择无需额外帮助。源端仅投影双方共享的正式事实，不向模型提供密码、验证码、金融账号或员工内部说明；动作仅指向原订单页面，AI 不代办支付、交号、确认或裁决。

源端确定性校验执行归属、事实版本、角色、动作和引用存在性；这不能证明每句自然语言都符合事实。启用实际模型前，至少对照以下成对场景人工验收：无支付尝试/原支付结果未知，待交号/已真实交付但未核对，取消前未交号/取消前已交号未回收，已到期未回收/已收回且材料未齐，资金已受理/机构确认成功。只替换催办话术、承诺未经确认到账、编造缺失金额与期限均不合格。

当前前端覆盖租客与号主的支付页、订单页、站内消息及实时提示；员工专属上下文/入口、主动问答和外部通知作为后续独立能力。测试使用隔离数据库和受控模型/工具响应验证编排及可靠性，不代表真实供应商内容质量和线上联调已经验收。

租号本地数据库验收仅允许隔离 MySQL，不允许 H2。租号仓库提供 `scripts/test-order-assistant.sh` 自动创建 MySQL 8.4 临时容器、执行本场景及 MCP/消息回归、退出清理。Creativity 测试继续使用隔离 PostgreSQL/Redis。
